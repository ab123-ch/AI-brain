# LLM Provider 单次调用自动重试设计

## 目标

为所有网络 LLM Provider 增加统一的传输级自动重试。一个任务包含多次 LLM 调用时，
某一次调用失败只重发该次调用的同一请求，不重新执行任务、主脑循环、既有工具调用或
此前已经成功的 LLM 调用。

默认每次 LLM 调用允许额外重试 5 次，即首次请求加 5 次重试，最多发送 6 次。重试
使用 1、2、4、8、16 秒指数退避。

## 与现有重试功能的边界

本功能与 Web 的 `retry_last_user_message` 是两个独立需求。

- `retry_last_user_message` 继续由 Web、WebSocket、会话管理和协作运行时负责。它会
  取消当前运行、截断最后一条用户消息之后的结果并重放整轮，现有行为不变。
- Provider 自动重试只存在于 `brain-llm` 内部。重试成功时，上层只观察到原来的单次
  LLM 调用；重试耗尽时，上层才收到最终错误。
- 主脑现有的 HTTP 200 空响应重试保持不变。空响应重试属于模型结果语义，不属于
  网络传输重试。
- 小说工作流、任务恢复、用户取消和工具级重试规则均不在本次范围内。

本次不修改 `ai-brain-cli` 的重试按钮、WebSocket 消息、会话截断、持久化失效边界或
任务重放代码。

## 适用范围

统一策略覆盖当前全部网络 Provider：

- OpenAI 兼容 Provider，包括 DeepSeek 等 Chat Completions 兼容服务；
- Gemini Provider；
- 两类 Provider 的普通完成、批量流式和增量流式入口。

本地 Echo Provider 不发起网络请求，因此不应用网络重试。未来新增网络 Provider 时，
必须复用同一重试策略和错误分类，不得重新引入错误字符串匹配。

## 架构

### 共享重试策略

在 `brain-llm` 内建立 Provider 无关的重试模块，负责：

- `RetryConfig` 及默认值；
- 指数退避计算；
- 可重试 HTTP 状态分类；
- `reqwest::Error` 及其错误源链的结构化分类；
- 当前尝试次数、最大尝试次数和重试日志所需的安全元数据。

`RetryConfig` 从 OpenAI 兼容实现中移到共享模块，但继续从 `brain_llm::RetryConfig`
公开导出，保持现有公共 API。OpenAI 兼容和 Gemini 客户端都使用同一默认配置：

```text
max_retries = 5
initial_backoff = 1s
max_backoff = 16s
```

### 单次逻辑调用

每个 `LlmProvider` 方法接到已经确定的 `ChatRequest` 后，先生成稳定的 Provider 请求体，
再进入内部尝试循环。所有尝试复用同一 URL、模型、请求头语义和序列化请求体；不得
重新读取会话、重新规划任务或重新执行工具。

Provider 返回成功结果后退出尝试循环。只有所有可用尝试耗尽，或遇到确定性不可重试
错误时，才向上层返回错误。因此主脑对该过程仍计为一次逻辑 LLM 调用。

### 普通完成

普通完成的尝试边界覆盖 HTTP 请求建立、发送和完整响应体读取。连接在收到完整响应前
中断时，可以重新发送当前请求。完整响应体已经收到但 JSON 或 Provider 契约不合法时，
按确定性响应错误处理，不自动重试。

### 批量流式

批量流式入口在成功后一次性返回 `Vec<StreamEvent>`，中间事件尚未暴露给调用方。
因此可将单次完整流读取作为一个尝试：中途出现可重试传输错误时丢弃该尝试已收集的
事件，等待退避后用同一请求重新建立流。

### 增量流式

增量流式入口只允许在首个 `StreamEvent` 交付上层之前自动重试。首个事件交付后如连接
中断，立即向现有流错误通道报告，不重新发送请求，避免文字、工具调用或副作用重复。

实现必须让“是否已交付首个事件”成为单次流调用的内部状态，而不是依靠内容字符串
推断。用户主动取消时立即停止当前请求和退避等待，不触发下一次尝试。

## 错误分类

### 可重试 HTTP 响应

只有以下 HTTP 状态允许自动重试：

- 408 Request Timeout；
- 429 Too Many Requests；
- 500 Internal Server Error；
- 502 Bad Gateway；
- 503 Service Unavailable；
- 504 Gateway Timeout。

现有确定性模型路由排除规则继续生效。响应体表明 `model_not_found`、
`model not found`、`no available channel` 或“没有可用渠道”时，即使状态是 503 也不
重试。

### 可重试网络错误

网络错误必须在 `reqwest::Error` 被转换为展示字符串之前分类。分类依据是 typed API
和标准错误源链，包括：

- 请求或连接超时；
- DNS/TCP 连接建立失败；
- `ConnectionReset`；
- `ConnectionAborted`；
- `BrokenPipe`；
- `NotConnected`；
- `TimedOut`；
- 在完整响应交付前的 `UnexpectedEof`。

不得使用 `error.to_string().contains(...)` 判断网络错误。本次生产故障中的
`error sending request for url` 没有暴露底层 Windows 10054 文本，正是字符串匹配
漏判的直接原因。

### 不可重试错误

以下错误立即返回：

- 400、401、403、404 等未列入白名单的 HTTP 状态；
- 确定性模型路由错误；
- Provider 配置、API Key 或认证配置错误；
- 请求序列化错误；
- 已完整收到响应后的 JSON/Provider 契约错误；
- 用户主动取消；
- 已向上层交付部分增量流之后的中断。

## 可观察性与错误输出

每次尝试记录 Provider、操作类型、逻辑调用内的尝试序号、最大尝试数、错误类别和下一次
退避时间。日志不得记录 API Key、Authorization、Cookie、完整请求正文、成功响应正文
或非成功响应体。

重试成功时记录成功发生在哪一次尝试。重试耗尽时保留最后一次错误作为面向上层的主要
原因，并附带总尝试次数；不得把多个可能含敏感信息的错误正文拼接进最终错误。

网络重试提供的是至少一次发送语义。如果服务器已经接受并处理请求，但响应在返回途中
丢失，客户端无法证明该请求未被计费，重新发送可能产生重复推理或计费。当前兼容接口
没有统一幂等键，设计不能虚假承诺恰好一次；通过仅重试明确的暂态失败、限制 5 次和不
在部分增量输出后重试来控制风险。

## 测试

### 共享分类单元测试

- 408、429、500、502、503、504 可重试；
- 400、401、403、404 不可重试；
- 普通 503 可重试，确定性模型路由 503 不可重试；
- 默认额外重试次数为 5；
- 退避序列严格为 1、2、4、8、16 秒；
- 网络分类不读取错误展示字符串。

### Provider 本地服务器测试

使用本地 TCP/HTTP 假服务器，不访问真实付费模型：

- 前 5 次接受请求后以连接重置失败，第 6 次返回成功，调用最终成功；
- 6 次接收到的请求体完全相同；
- 第 N 个逻辑调用失败时，服务器只再次收到第 N 个调用的请求体，前 N-1 个请求体各
  只出现一次；
- 5 次重试均失败时，第 6 次后返回最终错误，不发送第 7 次；
- 429/可重试 5xx 先失败后成功；
- 401 和确定性模型路由错误只发送一次；
- OpenAI 兼容和 Gemini 使用相同的次数与分类；
- 日志包含安全的重试元数据且不泄露请求、响应或凭据。

测试注入零时长退避配置，避免真实等待 31 秒；生产默认值仍验证为
1、2、4、8、16 秒。

### 流式测试

- 批量流在中断后丢弃未公开事件并重试，成功结果只包含成功尝试的事件；
- 增量流在首个事件前中断时重试；
- 增量流已经交付事件后中断时不重试，服务器请求计数不增加；
- 用户取消不会启动下一次尝试。

### 回归验证

- `brain-llm` 全量测试；
- `brain-main` 工具循环测试，证明 Provider 内部尝试不增加逻辑 LLM 调用次数，也不
  重放已完成工具；
- `ai-brain-cli` 现有 `retry_last_user_message`、会话管理和 WebSocket 测试，证明用户
  手动重试语义未改变；
- 工作区要求的 `cargo fmt`、严格 Clippy 和 workspace tests，并如实记录既有失败。

## 非目标

- 修改用户手动重试入口或语义；
- 从头重启整个任务；
- 重放已经成功的 LLM 或工具调用；
- Provider 自动切换、模型 fallback 或 API Key 轮换；
- 为不支持幂等键的第三方接口承诺恰好一次计费；
- 对已经公开的部分增量流做猜测式前缀去重。
