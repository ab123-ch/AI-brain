- Current Novel persistence synchronously translates Canon/project objects into graph nodes inside `brain-memory`; this combines domain policy, memory storage, and graph projection in one module.

## 2026-07-22 Generic Multi-Instance Brain Development Design

### User Architecture Decision
- Replace the special-purpose NovelBrain runtime with independent instances of one generic brain runtime.
- A conversation may initiate multiple instances with task-specific prompts, context, tools, models, and reasoning depth.
- The runtime must support both different-subtask collaboration and multiple independent attempts at the same task followed by cross-validation/adjudication.
- Memory recall/save, graph persistence/query, and parallel read/write behavior are first-class design concerns rather than adapters to add later.
- Multi-instance token amplification must be bounded by configuration, including instance counts, reasoning depth, and per-role model choice, without changing the architecture.

### Initial Architecture Constraint
- The execution center must be a persisted `TaskRun`, not a brain identity or mutable user conversation. The user session supplies intent and receives progress/results; task instances consume immutable, provenance-bearing context snapshots.
- Removing NovelBrain does not remove Novel domain logic. Canon, project revisions, immutable candidates, reviews, user approval, publication, and validators remain domain/workflow capabilities outside the generic agent runtime.
- Model calls must never execute while holding a repository, project, graph, or filesystem mutation lock. Read/compute/commit must be separate phases with optimistic revision checks or a short project-scoped command queue at commit time.
- Memory and graph have different authority levels: authoritative project/task facts live in domain repositories; memory is advisory retrieval; graph is a derived read model unless a separately declared graph-owned domain is introduced.
- Cost control must be enforced by a central budget ledger and scheduler, not left to prompts or independent instances.

### Reusable Runtime And Current Pressure Points
- The current generic sub-agent path already provides isolated LLM requests, tool allowlists, streaming thinking events, and background/synchronous execution. It is a useful extraction source for `AgentRuntime`, but its model selection is primarily `subagent.json -> brain_models.subagent -> main default`, not a task/role/instance policy hierarchy.
- Current request limits are mostly provider/model `max_tokens` and temperature. They do not yet represent a task-wide input/output/reasoning/cost budget shared by multiple instances.
- The resident Novel path creates a dedicated `novel` model client, confirming model routing is already injectable in composition, but it is tied to a special runtime identity that the target design removes.
- `Orchestrator`, `RealToolExecutor`, and Novel adapters currently share `Arc<tokio::sync::Mutex<PyramidMemoryBrain>>`. A multi-instance runtime must not fan out through this global mutable lock because unrelated recall, graph, and project operations would serialize and a slow operation could hold the whole memory subsystem.
- Graph reads/writes are exposed as ordinary tools (`graph_search_catalog`, node/detail/trace reads, and multiple add/link/index writes). Their implementation and storage transaction behavior must be separated from agent execution before write permissions are offered to parallel instances.
- Existing token-usage logging provides useful measurements, but scheduling needs a reservation/settlement ledger that can reject or degrade a fan-out before calls are launched.

### Storage And Concurrency Findings
- `brain-graph::GraphStore` uses one SQLite connection per opened store with `foreign_keys` and a five-second `busy_timeout`, but does not currently enable WAL. Node and edge writes are separate autocommit statements rather than one projection-batch transaction.
- Some nominal graph reads (`get_node_detail` and traversal paths) update access timestamps through `touch_nodes`, turning parallel retrieval into write-lock contention. Target query APIs must be side-effect free; access telemetry should be sampled and asynchronously aggregated.
- Graph mutation is currently available directly as ordinary agent tools. The target runtime should expose graph query capability to authorized instances, but instances should emit `MemoryProposal`/domain artifacts rather than performing authoritative graph writes.
- Novel Canon persistence currently performs a project-file commit and then mirrors every project/fact node and edge synchronously as a best-effort operation. The target should commit domain state plus an outbox event first and let an idempotent single-writer projection worker update the graph with a durable checkpoint.
- Current project JSON and memory JSON/JSONL stores are not suitable as shared parallel mutation primitives. Migration can preserve their data formats temporarily, but writes must pass through keyed command serialization and atomic replacement/append adapters until a transactional repository is introduced.
- The existing conversation-memory invalidation flow demonstrates useful revision fencing, but its process-global static lock is too broad for independent sessions/projects. The reusable principle is revision-checked snapshot/commit; the target lock scope should be a stable aggregate key and must never cover LLM execution.

### Task Runtime Findings
- The current generic `Agent` executor creates one fresh `Session`, builds a role-specific prompt/tool allowlist, starts one OS thread, and persists a standalone file manifest. This is a viable single-instance execution kernel, not yet a multi-instance task system.
- Current Agent manifests do not model `task_run_id`, parent/dependency edges, immutable context snapshot IDs, input/output contracts, budget reservations, review relationships, or aggregate revision. These must become first-class persisted fields rather than prompt text.
- The current dispatch bus prioritizes and forwards events/completion notifications, but synchronous Agent execution is explicitly handled outside it. It is not a scheduler and does not enforce global/provider/profile concurrency, fair queuing, cancellation, retry budgets, or task graph readiness.
- Each Agent currently receives broad tools based on a string subtype and may write files or graph data. Target profiles need typed capabilities and resource scopes; worker/reviewer instances should be read-only by default and return artifacts/proposals to deterministic commit handlers.
- Fresh instance sessions already support isolation. The target should preserve that property and replace ad hoc system-prompt construction with versioned `AgentProfile + PromptBundle + ContextSnapshot + ToolGrant + OutputSchema` resolution.
- Agent retry is currently local panic retry. Target retry semantics must distinguish provider/transient retry from new independent candidate generation and must debit both from the task budget.

### Novel Domain Retention
- Existing types for project revision, context references, task provenance, structured checks, user decisions, publication receipts, and lifecycle phases are valuable migration inputs. They should move into a dependency-independent `novel-domain`/`novel-application` boundary rather than remain owned by a special brain or MemoryBrain.
- Current Novel task state provides useful deterministic transition guards. The target workflow should preserve those guards while replacing `draft_version + embedded mutable draft` with immutable `artifact_id + content_hash + context_snapshot_id` references.
- Writer self-review, MainBrain review, and Canon delta are currently bundled into brain-specific contracts. Target contracts should split `CandidateDraft`, `ReviewReport`, `CanonDeltaProposal`, and `UserDecision`, each with exact observed artifact/snapshot hashes.
- The generic coordinator must not know Canon or publication rules. A versioned `NovelDevelopWorkflow` defines the DAG and invokes generic instances; `NovelApplicationService` owns domain transitions and commit authorization.
- Current dispatch includes `Novel` as a subtype/brain event. Migration should remove domain names from the generic executor/dispatch protocol and represent Novel work through workflow/profile IDs and ordinary task/artifact events.

### Reasoning And Token Policy Findings
- Token usage is already represented at provider/runtime layers and `ConversationRuntime` has a usage tracker plus input-token compaction threshold. These should feed the new task budget ledger rather than a separate best-effort log only.
- A `reasoning_effort` field exists in command-level Agent configuration, but the main generic sub-agent/provider request path does not expose one normalized reasoning contract. The target requires an explicit provider capability adapter.
- `ReasoningDepth` must not be a prompt-only adjective. Resolution should produce a bounded `ReasoningPolicy`: optional provider-native effort, reasoning-token allowance where supported, max tool-loop iterations, optional reflection passes, and output-token cap.

## 2026-07-22 Novel Brain Architecture Design Review

### User Clarification
- The requested output is an architecture-design critique, not a bug hunt.
- Preserve `docs/reviews/2026-07-22-novel-brain-architecture-issues.md` for later implementation hardening, but do not use its severity framing for the new review.

### Initial Design Reading
- The intended design deliberately defines NovelBrain as a resident domain brain, project workspace/cache, model runtime, task-state owner, revision context, self-reviewer, and publication initiator. These are multiple reasons to change and multiple lifecycle scales inside one abstraction.
- MainBrain is deliberately assigned environment preparation, user coordination, independent review, candidate presentation, and tool-level workflow progression. Its role combines conversational agent, application orchestrator, and reviewer.
- MemoryBrain is deliberately assigned task events, checkpoints, recall, Canon, conflict audit, publication journal, and graph projection. This is closer to a persistence/application subsystem than a cognitive peer.
- The design partitions the system primarily by named “brains.” Those boundaries do not line up cleanly with the domain's durable aggregates (`NovelProject`, `WritingTask`, `Draft`, `Review`, `Publication`) or with state/failure ownership.
- The original design explicitly allowed one global LLM generation and direct `brain-novel -> brain-memory` contract coupling. Several awkward runtime properties are therefore design choices, not accidental implementation bugs.
- Working thesis: NovelBrain should not be one global stateful brain. The stable concept is a `NovelWorkspace/NovelWorkflow` per project, while writer/reviewer LLMs should be replaceable, mostly stateless roles invoked by that workflow.

### Responsibility And Aggregate Analysis
- **The decomposition axis is wrong:** components are split by cognitive persona (`MainBrain`, `NovelBrain`, `MemoryBrain`) while the durable domain is split by project, writing task, immutable draft, review, approval, and publication. Persona boundaries are useful for prompts and cockpit visualization, but unstable as code/data ownership boundaries.
- **NovelBrain has incompatible lifecycle scales:** one process-resident supervisor owns many projects; each project owns long-lived Canon/workspace continuity; each writing task owns a shorter workflow; each model call is ephemeral. Combining these in one “resident brain” makes cache lifetime, domain lifetime, and worker lifetime appear equivalent.
- **The project is the natural aggregate root:** Canon revision, active branch, document structure, project policy, and active writing transaction all need one project-scoped consistency boundary. A global NovelBrain may supervise project runtimes, but should not itself be the aggregate or cognition owner.
- **The writer is a role, not a state owner:** an LLM writer should receive a context snapshot and produce an immutable candidate. Its conversation history is an optimization/input artifact, not the durable identity of the novel or task.
- **MainBrain is over-promoted into an application orchestrator:** translating user intent and presenting results belong to the interaction agent; resolving revisions, file hashes, context refs, review transitions, and publication sequencing belong to a deterministic Novel application service.
- **“Independent MainBrain review” is conceptually ambiguous:** the same conversational agent that framed the task and orchestrates tools is also treated as an independent reviewer. Review should be a dedicated role/context invoked by the workflow, backed by deterministic Canon/structure checks; it need not become another long-lived “brain.”
- **MemoryBrain is a subsystem bundle, not one domain capability:** recall/query memory, Novel Canon repository, task checkpoint store, audit event log, publication journal, conflict service, and graph projection have distinct ownership and change drivers. Calling them all memory hides transaction and source-of-truth boundaries.
- **Canon is domain state, not generic memory:** Confirmed facts, branch state, progress, and conflicts belong to the NovelProject domain. Memory/graph may index or retrieve them, but should not define the domain contract.
- **The current tool surface leaks internal workflow:** MainBrain receives low-level start/resume/review/user-decision/publish/status commands plus recall/consistency tools. This makes an LLM operate the state machine instead of issuing a high-level novel-writing intent to an application service.
- **The task contract mixes layers:** creative intent, project identity, optimistic revision, filesystem output path, content hashes/material refs, publication policy, and Web conversation provenance belong to different layers and should not be one MainBrain-authored DTO.
- **Three kinds of “memory” need explicit separation:** authoritative Canon, temporary working state/drafts, and advisory experience/style recall have different trust, retention, and mutation rules. A single MemoryBrain boundary obscures those semantics.
- **Draft creation, self-review, and Canon extraction are separate roles:** producing prose, judging prose, and extracting proposed domain facts in one model response couples creative sampling to validation and state mutation. They may reuse one provider, but should be separate workflow stages and contracts.
- **Residency should mean service availability and recoverable project continuity, not an immortal model conversation.** Correctness should come from persisted project/task snapshots; in-memory history is a cache that can be rebuilt or discarded.
- **Conversation and project are separate aggregates:** a Web message generation can originate or revise a task, but editing chat history should not be the primary ownership model for durable project work. Link them through provenance and explicit draft ownership, not shared lifecycle.
- **Events need one declared role:** either task events are the source of truth (event sourcing) or they are an audit/outbox derived from an atomic current-state commit. Keeping event plus checkpoint as co-authoritative representations is an architectural ambiguity.

### Architecture Options
- **Option A, keep the global resident brain and harden it:** smallest migration and preserves cockpit identity, but responsibility/lifecycle mismatch remains. It improves implementation without fixing the design model.
- **Option B, project-centric workflow with stateless model roles (recommended):** expose one stable Novel capability facade, route work to a project-scoped `NovelWorkspace/NovelWorkflow`, and invoke Writer, Reviewer, and CanonExtractor roles as replaceable calls. This aligns state, concurrency, recovery, and policy with the project/task aggregates.
- **Option C, turn Main/Novel/Reviewer/Memory into a general autonomous agent swarm:** visually consistent with the “many brains” metaphor but makes workflow determinism, authorization, transactions, and ownership harder. It is the wrong direction for controlled editorial production.
- The stable public product concept can remain “小说脑,” while internal code uses domain/service names. A cockpit node does not require one global mutable actor to own all project state.

### Recommended Source-Of-Truth Model
- `NovelProjectRepository`: project identity, branch, Confirmed Canon, progress, project policy, and revision.
- `WritingTaskRepository`: user intent, task state/version, clarification, candidate IDs, review results, and provenance.
- `DraftStore`: immutable candidate bodies addressed by draft ID/content hash; published artifact is a promoted immutable candidate.
- `PublicationCoordinator`: approval-bound publication process and idempotent commit; it coordinates project revision and artifact visibility.
- `ConversationStore`: user-facing chat only; it links to tasks but does not own or reconstruct project workflow state.
- `NovelMemoryService`: advisory experience/style recall and source resolution; it does not define Canon or task state.
- `NovelGraphProjection`: derived catalog/relationship read model fed by committed domain events.

### Recommended Collaboration Model
- MainBrain translates conversation into a high-level `NovelIntent`, asks user-facing questions, and explains candidates/results.
- `NovelApplicationService` resolves project revision, resources, context, policies, and workflow transitions; MainBrain does not assemble infrastructure fields.
- A project-scoped workflow invokes `WriterRole -> deterministic validators -> ReviewerRole -> CanonExtractorRole` as separate stages. Roles may share a provider but not a combined output contract.
- User approval is an application/transport command attached to an immutable candidate ID/hash, not a MainBrain reasoning step.
- Publication is triggered from the approved candidate and project revision; graph and recall projections subscribe after commit.

### Residency Decision
- Keep the Novel service resident for availability, scheduling, event streaming, and cache management.
- Make each project workspace independently loadable/evictable and the owner of project-scoped execution serialization.
- Treat LLM history as a disposable cache or persisted context summary, never as the source of task continuity.
- Treat Writer/Reviewer/Extractor executions as ephemeral jobs with explicit input/output; model identity and provider configuration remain injectable.

### Placement Inside The Wider AI-Brain Architecture
- The repository currently contains three architectural paradigms: legacy peer brains coordinated through BrainBus, a v2 tool-using MainBrain with temporary agents, and a typed domain workflow presented as resident NovelBrain.
- NovelBrain is not a peer `BrainAgent` on the legacy bus, and it is no longer a generic v2 subagent. MainBrain reaches it through ordinary tool dispatch, while its internals own domain state and persistence coordination. Architecturally it is an application service behind a brain-shaped facade.
- This hybrid can be retained during migration, but the internal contract should acknowledge the service boundary. Calling every capability a brain encourages adding identities and actors where a role, repository, validator, or workflow stage would be clearer.
- The overall `Orchestrator` already aggregates legacy brains, v2 MainBrain, EvalBrain, MemoryBrain, evolution components, dispatch, tools, and NovelBrain. It is a composition root plus runtime coordinator plus application service. A target architecture should reduce it to composition/lifecycle and move use-case coordination behind explicit application ports.

### Final Design Judgment
- Keep “NovelBrain” as a product capability/facade and cockpit projection, not as the global owner of every novel project and model conversation.
- Make `NovelApplicationService` the deterministic use-case boundary and `ProjectRuntime` the project-scoped execution boundary.
- Make `NovelProject`, `WritingTask`, immutable `CandidateDraft`, and `PublicationProcess` the explicit domain concepts.
- Return MainBrain to interaction/intent/presentation; return MemoryBrain to advisory recall and repository adapters; keep graph as a committed-event projection.
- Do not solve the current discomfort by adding more autonomous brains. Writer, Reviewer, and CanonExtractor are execution roles with explicit contracts, not new long-lived actors.
- The governing principle is: brain identities describe interaction/model roles; project workflows define business architecture.

### Confirmed Runtime Findings
- **Global head-of-line blocking:** `NovelBrain::run` receives one command and directly awaits `start_task`, `resume_task`, publication, status, and invalidation handlers before reading the next command. `start_task`/`resume_task` invoke the LLM path, so one project blocks every other project's commands.
- The independent shutdown `watch` avoids losing a shutdown request when the command queue is full, but it does not interrupt an already-running handler because the `select!` exists only around command receipt. Graceful shutdown can therefore wait indefinitely on the provider.
- Conversation invalidation/cancellation is also a queued command. It cannot preempt a generation already executing in the actor; cancelled MainBrain/Web callers can drop their reply while the NovelBrain continues work and persists intermediate state.
- Recovery is global and fail-fast: a bad checkpoint/publication for one project makes `recover()` return an error and marks the singleton brain degraded. This creates a potential one-project-poisons-all-projects failure domain; command behavior in degraded mode still needs tracing.
- The actor is over 2,000 lines including tests and owns recovery, cache eviction, generation orchestration, review transitions, publication transaction coordination, cancellation, telemetry, and status. The size reflects aggregate responsibilities, not merely verbose tests.
- Review validation is typed but shallow: a pass requires status enums, an empty issue list, summary text, and at least three distinct evidence-ref strings. It does not resolve those refs or prove a genuinely independent review. This is policy-shape validation, not evidence validation.
- `NovelSelfReviewVerdict::NeedsRevision` exists, but `validate_self_review` accepts only `verdict=Pass` with all six checks passing. The public model suggests a two-result self-review protocol while the implementation supports only a final-pass envelope; this is contract drift or dead modeling.
- **Hidden source-level coupling:** `brain-novel/src/runtime.rs` embeds `brain-main/skills/novel-writing-workflow/SKILL.md` through a cross-crate relative `include_str!`. Cargo does not model this dependency, and a MainBrain skill file is simultaneously used as NovelBrain's system policy.
- **Residency is not durable continuity:** per-project `ChatMessage` history lives only in `ProjectWorkspace.history`; checkpoints serialize `NovelTaskState`, which has no history. Actor restart restores active state with an empty history, and cache eviction discards history as well.
- **The context bound is message-count based, not token based.** Up to 12 messages can each contain the full task contract, Canon recall, consistency report, authorized documents, previous draft, and raw full-chapter assistant JSON. Revisions duplicate the previous chapter both in history and again in `previous_draft`, so context can grow by whole-manuscript chunks despite the nominal bound.
- The model is asked to produce full long-form prose, self-review, and a proposed Canon delta in one JSON response. This couples creative generation, evaluation, and structured state extraction into one sampling call and makes escaping/truncation/parser failure a normal long-output risk.
- `NovelTaskRequest.allow_web_research` is exposed in the contract, but `NovelModelRuntime` always sends `tools: None`; the capability flag currently has no execution path inside NovelBrain.
- The runtime sends `max_tokens: None` and `temperature: None` at the request boundary. This may delegate to provider defaults, but it means the NovelBrain runtime itself does not enforce a long-form output budget or creativity policy; configuration wiring needs confirmation in Orchestrator/client creation.

A failure can leave an event without the corresponding checkpoint, or leave in-memory state advanced while the caller receives an error.
- **Concrete cancellation inconsistency:** conversation invalidation mutates a removed task to `Cancelled`, then on persistence failure reinserts that already-cancelled object while returning an error. The caller sees cancellation failure, durable state may be old/partially written, and the actor sees a terminal cancelled task.

A stale command for an older task can evict the current in-memory task before its transition is rejected.

The runtime state machine rejects invalid transitions, but transaction progression and recovery intent are still selected by an LLM across user turns.

MainBrain also discovers, reads, and hashes materials before ResourcePort reads and verifies them again. Some verification is intentional, but the public workflow performs redundant domain queries and transfers storage details through the LLM.

Its only authorization is the state record produced through MainBrain tool calls, which is already not tied to a trusted user event. This is a systemic v2 permission gap with especially high impact in the Novel workflow.

Any project task can read any hashed UTF-8 file and create an artifact at any non-existing path inside the entire workspace.

- **Draft storage amplification:** every generated outcome is appended to the lifecycle JSONL with full prose, while the full current draft is also embedded in the checkpoint state. The same content then appears in MainBrain tool history, Web exchange persistence, and tracing logs. There is no event payload indirection/retention policy.
- Lifecycle event append and checkpoint replace are separate filesystem operations; event append is not fsynced. `active_checkpoint_for_project` scans all checkpoint files and silently chooses the newest nonterminal record, which masks rather than reports multiple-active-task invariant violations.
- Startup active-checkpoint discovery is inefficient: list projects, then scan the full checkpoint directory once per project. This is acceptable for tiny local data but will scale quadratically with project/task count.
- Both ResourcePort and MemoryPort implementations perform synchronous filesystem/CPU work while called from async tasks; MemoryPort also holds one global `Mutex<PyramidMemoryBrain>`. Long recalls, consistency scans, context reads, and `sync_all` can block unrelated memory operations/runtime workers.
- Downstream Canon commit does validate `delta.branch_id` against the project's active branch, so the local omission is eventually caught before Canon mutation. The validation happens after artifact write, however, which matters for failure semantics.
- **Publication can complete with Canon conflicts:** `commit_delta_internal` records conflicting proposed facts but accepts the remaining delta and returns `CommitReport.conflicts`; NovelBrain unconditionally marks the task `Completed`. Because the artifact is written before this check, published prose can assert facts that Confirmed Canon explicitly rejected.
- This contradicts the workflow text saying Canon conflicts should stop publication/re-review. Conflict detection should be a preflight gate or yield a non-completed publication state, not partial Canon success after immutable artifact publication.
- **Canon replacement is not crash-atomic:** `NovelMemoryStore::write_project` writes a `.tmp`, explicitly removes the existing project JSON, then renames the temp. A crash/error between remove and rename loses the Canon file; neither file nor parent directory is fsynced.
- Canon/project state is one ever-growing JSON aggregate. Every commit rewrites the full facts/conflicts/applied-publications document and graph mirroring re-walks all facts, increasing write amplification and crash exposure as a novel grows.
- `NovelTaskPhase` includes `SelfReview` and `StaleRevision`, but current state transitions do not enter them. `StaleRevision` is also nonterminal. The persisted state vocabulary is broader than executable behavior, creating misleading recovery/status contracts.
- Publication idempotency stores only applied publication IDs in the project. If Canon commit succeeds but the publication journal is not updated, retry returns a synthetic empty `CommitReport` with `graph_mirrored=true`, potentially losing the original accepted IDs/conflicts and misreporting graph state.
- **Validation occurs after irreversible artifact creation:** `begin_novel_publication` checks project/revision/path/hash but not active branch, fact validity, or Canon conflicts. Those checks run inside `complete_novel_publication`, after the exact artifact has been installed with no-overwrite semantics.
- A malformed model delta (for example wrong branch, empty fact title, or invalid confidence) therefore leaves an `ArtifactSaved` journal plus an immutable output file. The record remains “pending,” blocks all later publications for the project, and restart retries the same invalid delta.
- Recovery propagates that retry error out of the global `recover()` loop, so one stuck artifact/delta transaction can degrade the singleton NovelBrain for all projects. No public operator repair/replace/abort command exists for this post-artifact failure path.
- `NovelPublicationStatus::Failed` is defined but not assigned in the inspected publication path. Commit failures preserve `ArtifactSaved` plus an error string, conflating “retryable crash window” with “semantically invalid and needs intervention.”
- Graph projection failure does not fail publication and has no durable retry/outbox; `graph_mirrored=false` is only returned in the report. If that report is later lost in the commit/journal crash window, idempotent retry can incorrectly report `true`.

## 2026-07-16 Web Message Edit and Retry
- The requested semantics are a conversation fork, not a presentation-only edit: WebSession messages, MainBrain restored history, and conversation-derived MemoryBrain records must share one server-side cutoff.
- Retry is a constrained fork at the final visible user turn: keep that exact stored user message, remove any later turn artifacts, and invoke generation without appending a duplicate.
- Existing dirty-tree work contains the completed resident NovelBrain implementation and unrelated files; this task will make only additive, scoped changes on top of it.
- `ChatMessage` now has a stable message ID and an optional memory generation ID. Existing persisted sessions migrate missing message IDs on load; legacy messages remain generation-less so invalidation can fail closed.
- New queries, edits, and retries converge on one server-authoritative preparation path. MainBrain history is rebuilt from visible user/assistant messages before the regenerated turn on every Web query, preventing stale history from a previously active session.
- Editing retains the selected message ID, replaces its text, assigns a new generation, truncates every later chat/trace/tool message, invalidates all affected user generations, and immediately regenerates.
- Retry is rejected unless its ID identifies the last visible user message. A valid retry keeps its stored content and ID, assigns a new generation, truncates the old response/trace, and regenerates without adding another user message.
- Conversation memory is generation-scoped at L1. Invalidation moves superseded files to `l1-invalidated`, marks all derived layers stale before moving data, suppresses recall/profile/summary/graph/pending-analysis injection, and only clears staleness when concentration finishes at the same invalidation revision.
- A final audit caught a second-order leak in the original rebuild path: the concentration prompts still included old L2/L3/L4/profile/evaluation data as references, and the no-L1 fast path did not overwrite them. The rebuild now snapshots revision/staleness together, reads only active L1, supplies empty prior-derived inputs, overwrites every derived layer, and clears them explicitly when no active L1 remains.
- Rebuild publication is also revision-atomic: the current invalidation revision is rechecked while holding the conversation-memory lock, then graph projection and stale-marker clearing happen within that same critical section. A concurrent newer edit skips the graph callback and leaves derived memory unavailable.
- Legacy Web turns cannot be selectively removed from old shared L1 storage. Editing across one therefore leaves derived memory permanently suppressed, which is conservative but prevents deleted text from resurfacing.
- Novel task requests and follow-up gates carry their originating Web conversation generations. A fork cancels matching unpublished resident tasks and persists a Cancelled checkpoint; published artifacts, Completed tasks, and Confirmed Canon are intentionally not rolled back.
- Runtime brain exchanges are stored with their originating generation. Delayed responses from an invalidated generation are rejected by SessionManager instead of appearing under the regenerated branch.
- Query ownership is guarded per session across connections. All terminal paths release the guard, including invalid requests, cancellation, generation completion, send failure, and WebSocket disconnect.
- The UI renders edit controls on all identified user messages and a retry control only on the final user message. Editing is inline; both successful actions rely on the server's refreshed authoritative message list.
- Final verification passes: `brain-memory` 201/201 and deterministic `ai-brain-cli` 201/201 with the real-model query filtered. Browser screenshot verification remains unavailable because the in-app browser environment lacks required sandbox metadata.
