# 无后缀 Markdown 与实例定向唤醒设计

## 目标

本次变更包含两个相互独立但共同面向协作群聊体验的能力：

1. 文件预览在文件没有扩展名时，先根据内容判断是否为 Markdown；匹配成功则默认使用现有安全 Markdown 预览，否则保持当前文本编辑逻辑。
2. 实例回复中的显式 `@显示名` 可以定向唤醒同房间实例；被唤醒实例获得当前实例回复、原始用户消息以及发送实例本轮修改文件的冻结信息。

## 非目标

- 不把所有无后缀文本都当作 Markdown。
- 不改变有明确非 Markdown 后缀文件的现有打开方式。
- 不让前端代替服务端解析或派发实例回复中的 `@`。
- 不为模型增加“发送消息”工具，也不恢复旧的自动参与或全员辩论机制。
- 不把发送实例修改文件的正文自动注入接收实例，只提供绝对路径和变更类型，由接收实例按需读取。
- 不恢复归档实例。
- 不向接收实例注入发送实例的其他私有历史。

## 方案选择

### 无后缀文件

采用内容感知的 Markdown 判定。文件加载完成后，若名称没有扩展名，则使用页面已经加载的 `marked` 词法分析结果检查结构化 Markdown token。标题、列表、引用、代码块、表格、分隔线、链接等明确结构可判定为 Markdown；只有普通段落和空白时仍作为文本打开。

没有采用“所有无后缀文件都按 Markdown”方案，因为普通配置、日志和代码片段会被误判。也不采用自定义正则集合完整解析 Markdown，因为现有页面已经依赖 `marked`，重复实现语法会产生不一致。

### 实例间定向唤醒

采用服务端事务派发。实例回复完成时，仓储层在同一个 SQLite `IMMEDIATE` 事务中追加回复事件、解析规范显示名、恢复符合条件的休眠实例，并创建 Direct Inbox。这样断线、重启、多客户端以及重复完成回放都共享同一持久化事实。

没有采用前端观察回复后再发送命令的方案，因为后台运行或断线时会丢失派发，且多个客户端可能重复派发。没有采用模型工具调用方案，因为用户可见的 `@` 文本本身就是意图，额外工具调用会让行为依赖模型是否正确调用工具。

## 无后缀 Markdown 判定

### 判定顺序

1. `.md` 和 `.markdown` 文件继续直接支持 Markdown，并默认进入预览。
2. 有其他扩展名的文件不做内容猜测，保持当前编辑模式。
3. 无扩展名文件等待快照正文加载后再判定。
4. `marked` 不可用、解析失败或只得到普通段落/空白时，回退当前文本编辑模式。
5. 匹配到明确 Markdown 结构时，标记本次打开会话支持预览并默认进入预览模式。

判定只决定打开时的默认模式和是否显示预览切换，不改变保存格式。Markdown 输出继续经过 `DOMPurify` 清洗，并沿用现有代码高亮与选择引用功能。

### 状态更新

初始点击文件时还没有正文，因此不再仅根据文件名永久确定模式。`applyLocalFileSnapshot` 在写入最新正文后计算本次会话的 Markdown 能力；随后再同步预览/编辑控件。明确 Markdown 后缀始终支持预览，无后缀文件以当前已加载快照为准。

## 实例回复中的 `@`

### 匹配规则

- 仅匹配同房间非归档实例的完整规范显示名，形式为 `@显示名`；`@` 前和名称后都必须是正文边界，避免从邮箱、较长名称或普通单词中截取命中。
- 同一回复中重复提及同一实例只产生一次派发。
- 发送实例提及自己时忽略。
- 最长显示名优先，避免 `@A` 抢先匹配 `@AB`。
- 归档实例不恢复、不创建 Inbox，也不让发送实例的回复失败。

匹配与派发发生在服务端。前端只展示回复事件中服务端返回的收件人，不参与权威解析。

### 生命周期和排队

- `active`：创建一个 Direct Inbox；如果实例已有运行，沿用现有同线程/成员调度规则排队。
- `sleeping`：在成功创建 Direct Inbox 的同一事务内永久改为 `active`，更新唤醒时间与成员版本。
- `sleep_after_current`：取消待休眠状态，永久改为 `active`，新 Inbox 在当前运行之后排队。
- `archived`：忽略，不恢复。

休眠恢复与该目标的 Inbox 创建是目标级原子操作：如果容量或回复链限制不允许创建 Inbox，则不单独恢复该实例。存储错误会回滚整个完成事务，由既有恢复机制重试；策略性跳过某个目标不会让发送实例的正常回复失败。

### 循环保护

实例间定向唤醒继续使用现有配置：

- `max_debate_depth`
- `max_group_replies_per_conversation`
- `max_group_replies_per_member`
- 每成员和每房间 Inbox 容量

超过限制的提及保留在公开消息正文中，但不创建新的执行。`room_event_recipients` 和 Direct Inbox 只记录实际成功派发的目标；数据库唯一约束继续保证同一来源事件对同一成员最多一个 Inbox。

## 持久数据和事件

不新增数据库表。现有数据足以重建权威交接信息：

- `room_events` 保存 A 的完整回复、发送者、对话根事件和冻结工作目录。
- `room_event_recipients` 保存实际成功派发给 B 的关系。
- `member_inbox_items` 保存 B 的 Direct 工作项。
- `collaboration_run_changed_files` 通过 A 回复事件的 `run_id` 提供绝对路径和 `added`/`modified` 类型。

完成事务对每个成功目标写收件人、投递和 Inbox；若恢复了休眠成员，同时更新成员状态。事务提交后沿用 room outbox 发布权威快照。

幂等完成重放使用既有 `run-result:<run_id>` 事件键和 Inbox 唯一约束，不重复恢复成员、追加事件或创建任务。

## 冻结上下文

### Claim 交接信息

Direct Inbox 的来源是 A 的 `member_message` 时，Claim 额外携带一个结构化 member handoff：

- `source_member`：A 的成员 ID、显示名、回复事件 ID、序号、正文哈希和本轮冻结工作目录。
- `root_user_reference`：该对话链 `conversation_root_event_id` 指向的原始用户消息及内容哈希。
- `changed_files`：A 本轮所有去重、排序后的绝对路径和变更类型。

普通用户 Direct Claim 不携带 member handoff，继续使用当前 v4 路径。

### ContextSnapshot

实例转交任务使用 `collaboration-task-v5`：

1. `CurrentInput` 是 A 的完整回复，并明确标注发送实例身份。
2. 原始用户消息以 required `ConversationReference` 冻结，保证它即使离开最近三条用户消息窗口仍可用。
3. A 有文件变更时，以 required `Artifact` 块冻结路径和变更类型；没有变更时不创建空块。
4. 现有最近三条用户消息与 B 自己回复的历史投影保持不变，仍作为 optional blocks。
5. 若 A 的直接父事件与根用户事件相同，复用同一个引用块，避免重复正文。

任务的 `resolved_config` 同时保存 member handoff、上下文快照 ID 和内容哈希。启动恢复和 durable result 投影必须重新从 Claim 校验发送者、根用户引用、文件路径列表以及 required blocks；身份不一致的历史任务按现有单项隔离语义处理，数据库或 I/O 错误仍保持致命错误分类。

### 工具工作目录

B 的工具执行目录继续取来源事件冻结的 `execution_working_directory`。A 修改文件列表中的路径为绝对路径，因此 B 可以直接读取；相对路径仍按同一冻结目录解析，运行期间不读取或修改进程全局 cwd。

## 错误与兼容性

- v3/v4 已持久任务保持可恢复；只有新创建的实例转交任务使用 v5。
- 找不到有效根用户事件、来源事件身份损坏或文件路径快照不一致时，该 Inbox/历史结果单项失败或隔离，不拖垮后续健康任务。
- Markdown 内容识别失败完全回退现有编辑器，不阻断文件打开。
- `marked` 或 `DOMPurify` 不可用时保持纯文本安全显示。
- A 回复中的无效、归档、自身或超限提及不会把 A 已生成的有效回答转为失败。

## 关键测试

遵循只覆盖关键功能的要求，不展开排列组合：

1. 一个纯前端测试同时证明：标准无后缀 Markdown 默认预览，普通无后缀文本回退编辑模式，有明确非 Markdown 后缀不猜测。
2. 一个真实仓储测试证明：A 的一次回复重复提及 active B、sleeping C、archived D 和自身时，B/C 各只有一个 Direct Inbox，C 永久恢复 active，D/自身没有 Inbox。
3. 一个上下文持久化测试证明：B 的 v5 Task/ContextSnapshot 包含 A 完整回复、根用户引用和 A 的绝对变更文件路径及类型，且 B 现有历史投影不包含 A 的额外历史。
4. 一个恢复测试证明：重开仓储后 v5 Claim/Task 身份校验仍通过；篡改根用户引用或文件列表会被拒绝。

受影响模块的现有定向测试继续作为回归门禁，包括文件编辑器、协作仓储、协作 runtime、静态资源与格式检查。
