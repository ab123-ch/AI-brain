# AI Brain Agent 架构设计方案

> 日期：2026-04-03
> 状态：初始方案（草案）

---

## 一、项目定位

构建一个模拟人脑工作机制的多 Agent 系统。多个专门化的副脑 Agent 常驻后台运行，各司其职，通过公共消息总线并行通信，协同处理外部输入的任务。系统具备学习、进化能力——越用越聪明。

---

## 二、核心需求

| 维度 | 决策 |
|------|------|
| 副脑职能 | 高度抽象，底层规则驱动，可学习进化 |
| 运行模式 | 并行广播，所有副脑同时收到消息 |
| 技术栈 | Rust 核心 + Python AI 层 |
| 副脑数量 | 最小 6 个核心 + 自然进化 |
| 核心副脑 | 感知 / 推理 / 记忆 / 执行 / 校验 / 评估 |
| 输入方式 | CLI + API 并行 |
| LLM 策略 | 快思考(规则) + 慢思考(LLM) 分层 |

## 四、6 个核心副脑

### 4.1 感知脑 (Sensory Cortex)

**类比**：感觉皮层 — 大脑的输入门户

**核心职能**：
- 接收外部输入（CLI、API、MCP、Hook）
- 解析输入格式（文本、JSON、文件变更事件等）
- 提取意图和关键信息
- 分类打标（任务类型、紧急度、领域标签）
- 投递到公共消息总线

**底层规则**：
- 所有外部输入必须经过感知脑
- 感知脑不做深度推理，只做解析和分类
- 分类结果附带标签，帮助其他副脑快速判断相关性

### 4.2 推理脑 (Prefrontal Cortex)

**类比**：前额叶 — 大脑的思考中枢

**核心职能**：
- 对所有信息进行推理思考
- 存储推理路径和决策模式
- 积累经验，类似任务可复用历史推理路径

**底层规则**：
- 遇到任何信息都尝试思考
- 记录思考路径（问题 → 分析 → 推理 → 结论）
- 成功的思考路径存入经验库，失败的不丢弃但标记为反面案例
- 下次遇到类似任务优先匹配历史经验

**经验存储格式**：
```
{
  experience_id: "exp_001",
  trigger_pattern: "代码bug修复",
  reasoning_path: ["分析→定位→修复→验证"],
  tools_used: ["Read", "Grep", "Edit", "Bash"],
  success_rate: 0.92,
  last_used: "2026-04-03",
  use_count: 47
}
```

### 4.3 记忆脑 (Hippocampus)

**类比**：海马体 — 大脑的记忆管理中心

**核心职能**：
- 记忆的存取、索引、召回
- 短期记忆（当前会话）和长期记忆（跨会话）的转化
- 记忆巩固（从详细的原始信息中提取要点）
- 空闲时对所有记忆进行总结、提炼、学习

**底层规则（核心设计决策）**：
- **所有原始记忆永久保留，永不删除**（纯文件存储）
- 召回行为受衰减控制，但数据本身始终在磁盘上
- 不使用向量数据库，使用纯文件 + 关键词索引
- 记忆金字塔：原始层 → 总结层，越往上越精炼
- 空闲时触发任务级深度巩固（总结思考路径、犯错原因、经验提炼）
- 物理删除仅在磁盘空间不足时触发（清理最不重要的记忆）

#### 记忆脑的分层架构：总结金字塔 + 永久原始层

> **核心设计决策**：所有原始记忆永久保留为文件，永不删除。遗忘 = 召回时跳过，不是物理删除。
> 总结金字塔叠在原始层之上，越往上越精炼。不使用向量数据库，纯文件 + 关键词索引。

```
记忆脑 (Hippocampus)
│
├── L0: 任务总结层 (Task Summary)
│   ├── 来源: 空闲时深度巩固产出
│   ├── 职责: 一个完整任务的端到端总结
│   ├── 内容:
│   │   ├── 任务目标 + 最终结果
│   │   ├── 完整思考路径（关键决策点）
│   │   ├── 犯过的错 + 原因 + 如何避免
│   │   ├── 修改的文件列表 + 修改原因
│   │   ├── 下次同类任务的快捷路径建议
│   │   └── 涉及的模块、工具、依赖
│   ├── 存储: ~/.ai-brain/memory/long-term/tasks/{task-id}.json
│   ├── 索引: 按业务域/技术栈/任务类型建立关键词索引
│   └── 类比: 事后复盘报告（提炼后的经验）
│
├── L1: 事件索引层 (Event Index)
│   ├── 来源: 每隔一段时间或达到阈值时自动触发总结
│   ├── 职责: 时间线摘要 + 关键事件索引
│   ├── 内容:
│   │   ├── 时间段内完成的所有任务概要
│   │   ├── 重要决策记录（做了什么选择、为什么）
│   │   ├── 关键文件变更记录
│   │   └── 用户偏好和行为模式更新
│   ├── 存储: ~/.ai-brain/memory/short-term/events/{date}.json
│   ├── 索引: 关键词 HashMap（tag → memory_id 列表）
│   └── 类比: 日记摘要（一天的精华）
│
├── L2: 短期记忆层 (Short-term Memory)
│   ├── 来源: 会话进行中的实时记忆
│   ├── 职责: 当前活跃的上下文、最近对话的摘要
│   ├── 内容:
│   │   ├── 最近 N 条对话的关键信息
│   │   ├── 用户偏好（临时）
│   │   ├── 上下文片段（文件路径、变量名等）
│   │   └── 待办事项和未完成的任务
│   ├── 存储: ~/.ai-brain/memory/short-term/recent.json
│   ├── 召回优先级: importance 控制，但数据永不删除
│   └── 类比: 工作台上的便签（随时可看）
│
├── L3: 原始记忆层 (Raw Memory) — 永久保留
│   ├── 来源: 复用 claw-code-parity session.rs
│   ├── 职责: 所有原始对话和操作的完整记录
│   ├── 内容:
│   │   ├── 完整的对话历史（用户输入 + 副脑响应）
│   │   ├── 工具调用记录（调用参数 + 返回结果）
│   │   ├── 错误日志（异常堆栈 + 上下文）
│   │   └── 系统事件（启动/关闭/配置变更）
│   ├── 存储: ~/.ai-brain/sessions/{session-id}.jsonl
│   ├── 压缩: Token 超限时复用 compact.rs 生成摘要，但原始文件保留
│   ├── 永不删除: 即使被总结覆盖，原始文件始终保留
│   └── 类比: 大脑的完整体验记录（潜意识层面，平时想不起来但一直在）
│
└── 记忆流转机制:
    │
    ├── 写入路径（始终写入 L3）:
    │   副脑产生信息 → 记忆脑接收
    │   → 始终写入 L3（原始层，永久保留）
    │   → 同时写入 L2（短期层，带 importance 标记）
    │   → importance > 0.7 → 标记为巩固候选
    │
    ├── 读取路径（从上往下查，命中即停）:
    │   副脑请求记忆 → 记忆脑检索
    │   → L0 任务总结匹配（经验库关键词匹配）
    │   → L1 事件索引匹配（时间段 + 关键词）
    │   → L2 短期记忆匹配（最近活跃）
    │   → L3 原始记忆回溯（需要细节时才查）
    │   → 合并结果 + 标注来源 + 可信度
    │
    ├── 巩固路径（空闲时深度执行）:
    │   空闲触发 → 扫描所有层级
    │   → 从 L3 原始记忆中提取任务级总结 → 写入 L0
    │   → 从 L2 短期记忆中提炼事件索引 → 写入 L1
    │   → 总结内容: 思考路径、犯错原因、如何避免、
    │   │            改了哪些文件、下次怎么做更快
    │   → L0 经验写入推理脑的经验库
    │
    ├── 召回优先级（衰减影响的是召回行为，不是存储）:
    │   importance > 0.5  → 正常召回
    │   importance 0.2~0.5 → 需要强关键词线索才召回（"好像见过"）
    │   importance < 0.2  → 不主动召回，但数据仍在 L3
    │
    └── 物理删除（仅在磁盘空间不足时）:
        扫描所有 importance < 0.1 的记忆
        → 按重要性从低到高排序
        → 逐个删除直到空间恢复到安全线
        → 记录清理日志
```

#### 记忆脑的数据结构

```rust
/// 一条记忆记录
struct MemoryEntry {
    id: String,
    content: String,                    // 记忆内容
    tags: Vec<String>,                  // 标签（用于关键词检索）
    layer: MemoryLayer,                 // L0/L1/L2/L3
    importance: f64,                    // 召回优先级 [0.0, 1.0]（不影响存储）
    source: KnowledgeSource,            // 来源（WebSearch/LLM/用户确认/其他副脑）
    confidence: f64,                    // 来源可信度
    reference_count: u32,               // 被引用次数
    created_at: DateTime<Utc>,
    last_accessed: DateTime<Utc>,
    consolidated: bool,                 // 是否已被总结到上层
}

enum MemoryLayer {
    TaskSummary,  // L0: 任务总结（深度巩固产出）
    EventIndex,   // L1: 事件索引（时间段摘要）
    ShortTerm,    // L2: 短期记忆（活跃上下文）
    Raw,          // L3: 原始记忆（永久保留）
}
```

#### 记忆脑的快思考/慢思考

```
快思考（不调 LLM，纯文件 + 关键词匹配）:
├── L0 经验匹配: trigger_pattern 关键词匹配
├── L1 事件匹配: 时间段 + tag 集合交集
├── L2 精确匹配: 当前会话消息 ID / 工具调用 ID
├── L3 回溯: 仅在需要细节时按 ID 读取原始文件
└── 返回: 匹配的记忆列表 + 来源 + 可信度

慢思考（调 LLM）:
├── 快思考结果不够或需要理解语义
├── 粗筛一批候选记忆（最多 20 条）
├── 让 LLM 判断哪些相关，提取要点
├── 记忆巩固（从原始信息提取任务级总结）
└── 输出: 精炼后的记忆 + 总结

不使用向量数据库:
├── 初期数据量小，关键词索引足够
├── 向量数据库在长期记忆 > 10000 条且召回率 < 70% 时再引入
└── 届时作为可选的 Python MCP Server 插件，不影响 Rust 层
```

#### 记忆脑的快思考/慢思考

```
快思考（不调 LLM）:
├── Layer 1 精确匹配: 消息 ID / 工具调用 ID
├── Layer 2 关键词匹配: tags ∩ message.tags
├── Layer 3 经验匹配: trigger_pattern 相似度
└── 返回: 匹配的记忆列表 + 来源 + 可信度

慢思考（调 LLM）:
├── 需要理解语义才能检索的场景
├── 记忆巩固（从原始信息提取要点）
├── 记忆冲突解决（多条记忆互相矛盾时选择最可信的）
└── Python 向量服务: embedding → semantic search
```

### 4.4 执行脑 (Motor Cortex)

**类比**：运动皮层 — 大脑的行动输出

**核心职能**：
- 工具调用（MCP、内置工具、插件）
- 代码执行
- 文件操作
- 外部系统交互

**底层规则**：
- 只执行经过校验脑审核通过的操作
- 维护工具注册表，记录每个工具的能力和适用场景
- 执行结果反馈给主脑和记忆脑
- 执行失败时记录失败原因，供推理脑分析

### 4.5 校验脑 (ACC + Basal Ganglia + Error Monitoring Network)

**类比**：前扣带回 + 基底节 + 错误监测网络 — 安全控制 + 真实性把关

**核心职能**：

**① 安全性校验（行为抑制）**
- 校验执行脑的工具调用是否合理
- 判断命令是否安全
- 对高危行为进行拦截或要求用户授权

**② 真实性校验（错误监测）**
- 追踪回答的信息来源（WebSearch？记忆？LLM推理？）
- 评估来源可信度并评分
- 交叉验证多个来源的一致性
- 对低可信度回答标注警告和建议验证

**底层规则**：

**安全性规则**：
- 所有执行脑的行动必须经过校验脑
- 维护高危行为规则库（如 `rm -rf`、删除数据库等）
- 低风险操作自动放行，中风险需确认，高风险必须用户授权
- 校验结果记录，持续优化规则库

**真实性规则（来源可信度评分）**：

| 信息来源组合 | 可信度 | 处理方式 |
|-------------|--------|---------|
| 纯记忆（无验证） | 0.50 | 必须标注警告 + 建议验证 |
| 纯 LLM 推理（无外部数据） | 0.60 | 标注来源，提示可进一步确认 |
| WebSearch 单一来源 | 0.75 | 标注来源，提示可进一步确认 |
| WebSearch + 记忆交叉验证 | 0.95 | 直接输出 |
| 多次 WebSearch 交叉验证 | 0.95 | 直接输出 |
| 用户确认过的信息 | 1.00 | 直接输出 |

**可信度输出策略**：
- 可信度 < 0.60 → 必须标注警告，建议用户验证后再采纳
- 可信度 0.60-0.80 → 标注信息来源，提示可进一步确认
- 可信度 > 0.80 → 直接输出，无需额外提示

### 4.6 评估脑 (Brainstem Reflex — 上下文评估)

**类比**：脑干反射弧 — 固定回路，无状态，执行后自毁

**核心特征：无状态副脑**
- 没有自己的长期记忆，不积累上下文
- 每次启动都是空白状态，只加载固定的 system prompt
- 执行完评估后自动清空所有上下文
- 类似大脑的反射弧：刺激 → 固定反应 → 结束

**核心职能**：
- 监控所有副脑的上下文窗口健康度
- 评估哪些上下文可以安全删除
- 评估删除后对后续推理的影响
- 执行上下文瘦身（将决策权交给主脑执行）

**工作周期**：

```
评估脑生命周期（每次独立）:

  ① 加载 system prompt（固定规则）
  │   · Token 上限检查规则
  │   · 冗余检测规则
  │   · 删除影响评估规则
  │   · 瘦身策略规则
  │
  ② 接收其他副脑的上下文快照
  │   · 推理脑: [85% 使用, 200 条消息]
  │   · 记忆脑: [40% 使用, 50 条消息]
  │   · 执行脑: [60% 使用, 80 条消息]
  │   · 校验脑: [30% 使用, 20 条消息]
  │
  ③ 按固定规则执行评估
  │   · Token 用量是否接近上限？
  │   · 是否有重复/冗余内容？
  │   · 是否有过时信息（已被新操作推翻的旧结论）？
  │   · 是否有低价值信息（工具调用的中间输出）？
  │
  ④ 输出瘦身指令给主脑
  │   · 安全删除: 有 L1/L0 备份的详细过程 → 删除
  │   · 压缩替换: 多轮工具输出 → 替换为 1 句摘要
  │   · 保留关键: 决策点、错误教训、最终结论 → 必须保留
  │   · 健康度报告: 每个副脑的状态评分
  │
  ⑤ 自毁：清空自身所有上下文
      · 保留: system prompt（下次重载）
      · 保留: 评估规则（硬编码）
      · 清空: 对话历史、中间状态、临时变量
      · 清空: 接收到的其他副脑快照数据
      → 等待下次触发
```

**触发条件**（由主脑控制）：
- 系统空闲 5 分钟以上
- 任何副脑上下文使用率超过 80%
- 一个完整任务完成后
- 用户手动触发 `/evaluate`

**上下文健康度评分规则**：

```
健康度 = f(使用率, 冗余度, 过时率, 关键信息密度)

使用率 < 50%    → 健康
使用率 50-70%   → 正常
使用率 70-85%   → 警告（建议瘦身）
使用率 > 85%    → 危险（必须瘦身）
使用率 > 95%    → 紧急（立即强制压缩）

冗余度评估:
  · 连续 3 轮以上的重复性工具输出 → 标记为可压缩
  · 已被后续操作推翻的旧结论 → 标记为可删除
  · 纯信息展示无决策价值的输出 → 标记为可删除

关键信息保护（不可删除）:
  · 决策点及原因
  · 犯过的错误和修正过程
  · 最终结论和产出物
  · 用户明确肯定/否定的内容
```
- 所有执行脑的行动必须经过校验脑
- 维护高危行为规则库（如 `rm -rf`、删除数据库等）
- 低风险操作自动放行，中风险需确认，高风险必须用户授权
- 校验结果记录，持续优化规则库

## 五、核心机制

### 5.1 三通道消息架构

系统采用三个独立消息通道，统一所有通信为消息传递，消除函数调用。

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  通道 1: 广播通道 (Broadcast)                                │
│  ├── 生产者: 感知脑                                         │
│  ├── 消费者: 所有副脑（含主脑）                              │
│  ├── 用途: 感知脑将解析后的输入广播给所有副脑                  │
│  └── 特点: 所有副脑并行接收，各自独立判断                    │
│                                                             │
│  通道 2: 协作通道 (Collaboration)                            │
│  ├── 生产者: 任意副脑                                       │
│  ├── 消费者: 指定目标副脑 + 主脑(只读抄送)                   │
│  ├── 用途: 副脑之间互相请求协助                              │
│  └── 特点: 点对点/点对多，支持请求-响应配对                  │
│                                                             │
│  通道 3: 结果通道 (Result)                                   │
│  ├── 生产者: 所有副脑                                       │
│  ├── 消费者: 主脑                                           │
│  ├── 用途: 副脑提交快思考/慢思考结果                        │
│  └── 特点: 主脑汇总后做最终决策                             │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**各脑在三通道中的角色**：

```
          │ 通道1 广播  │ 通道2 协作     │ 通道3 结果
──────────┼─────────────┼───────────────┼──────────────
感知脑    │ 生产者      │ 不参与         │ 不参与
推理脑    │ 消费者      │ 生产者/消费者  │ 生产者
记忆脑    │ 消费者      │ 生产者/消费者  │ 生产者
执行脑    │ 消费者      │ 生产者/消费者  │ 生产者
校验脑    │ 消费者      │ 生产者/消费者  │ 生产者
评估脑    │ 不参与      │ 不参与         │ 不参与(仅空闲工作)
主脑      │ 消费者      │ 只读监听       │ 消费者(汇总)
```

**通道 2 协作消息结构**：

```rust
struct CollaborationMessage {
    id: String,                     // 消息唯一 ID
    from: String,                   // 发送方副脑名称
    to: Vec<String>,                // 接收方副脑名称列表
    correlation_id: Option<String>, // 请求-响应配对（回复时填请求 ID）
    hop_count: u32,                 // 转发次数（>3 丢弃，防循环）
    priority: MessagePriority,      // 优先级
    content: String,                // 协作内容
}
```

**防循环机制**：
- 每条协作消息携带 `hop_count`，每转发一次 +1
- `hop_count > 3` 时丢弃消息并通知主脑
- 主脑通过只读监听通道 2，感知所有副脑的协作状态

### 5.2 感知脑设计（纯 LLM 解析）

感知脑是系统**唯一入口**，负责接收外部输入、LLM 解析、投递广播。

```
外部输入 (CLI / API / MCP / Hook)
         │
         ▼
┌───────────────────────────────────────┐
│         感知脑 (Sensory Brain)         │
│                                       │
│  LLM: haiku (最快最便宜)              │
│  Prompt: 自然语言描述输入意图          │
│  输出: 自然语言描述（非 JSON）         │
│                                       │
│  不做: 打标、分类、意图提取            │
│  只做: 理解 + 描述 + 注入环境上下文    │
│                                       │
└───────────────────┬───────────────────┘
                    │
                    ▼
              投递到广播通道
```

**解析 Prompt**：

```
用简洁的自然语言描述用户输入的内容和意图。
同时补充以下环境信息：
- 当前日期: {date}
- 工作目录: {cwd}
- git 分支: {branch}

直接输出描述，不需要任何格式。
```

**输出示例**：
```
输入: "帮我开发一个订舱详情查询接口"
输出: "用户要开发订舱详情查询API接口。当前在 ship-core 项目的 feature/booking-detail 分支上。"
```

**降级策略**（LLM 不可用时）：
```
if 感知脑 LLM 调用失败 or 超时 2s:
    → 直接将原始输入投递到广播通道
    → 标记 "未解析"
    → 下游副脑收到后走慢思考路径
```

**关键设计原则**：感知脑不替下游做判断。分类、打标、意图提取的工作交给每个副脑自己——它们各自关心不同的维度，比感知脑统一分类更准确。

### 5.3 快思考 + 慢思考 (Dual Process)

每个副脑内部都有两层处理机制：

```
快思考 (System 1) — 本地规则引擎
├── 模式匹配: 输入与历史经验的相似度
├── 规则判断: 预定义的 if-then 规则
├── 阈值决策: 简单场景直接返回，不调 LLM
└── 延迟: ~10ms

慢思考 (System 2) — LLM 调用
├── 复杂推理: 需要深度分析的场景
├── 经验生成: 存储新的推理路径
├── 上下文理解: 需要理解语义的场景
└── 延迟: ~1-5s

判断逻辑:
  输入 → 快思考匹配 → 命中且置信度 > 阈值 → 直接返回
                    → 未命中或置信度低 → 慢思考 → 存储经验
```

### 5.4 消息流转流程

```
用户: "帮我开发订舱详情查询接口"

Step 1: 感知脑接收 + LLM 解析 + 投递广播通道
        "用户要开发订舱详情查询API接口..."

Step 2: 通道1广播 → 所有副脑并行快思考
        ├── 推理脑 → 通道3: "相关(0.9), 需要开发, 建议参考历史"
        ├── 记忆脑 → 通道3: "相关(0.7), 找到历史：订舱列表接口"
        ├── 执行脑 → 通道3: "相关(0.8), 需要工具调用"
        ├── 校验脑 → 通道3: "安全(低风险)"
        └── 主脑   → 监听通道1, 等待通道3结果

Step 3: 主脑汇总通道3结果 → 权重排序 → 决策
        → 调度推理脑慢思考（通过通道2发送调度指令）

Step 4: 推理脑慢思考过程中需要精确记忆
        → 通道2: 推理脑 → 记忆脑 "召回订舱接口开发模式"
        → 通道2: 记忆脑 → 推理脑 "HttpParseService + UserLoginInterceptor"
        （主脑只读监听通道2，知道副脑在协作中）

Step 5: 推理脑完成慢思考 → 通道3提交方案
        → 校验脑审核 → 通道3提交校验结果
        → 主脑汇总 → 输出给用户
```

### 5.5 主脑职责

主脑不是入口，而是**裁判 + 调度员**：

```
① 监听广播通道(通道1)
   → 知道用户输入了什么
   → 记录任务上下文

② 收集结果通道(通道3)的响应
   → 按权重排序
   → 决定哪些副脑需要慢思考

③ 只读监听协作通道(通道2)
   → 知道副脑们在协作什么
   → 不会超时中断
   → 不会重复调度

④ 调度慢思考
   → 通过通道2发送调度指令给指定副脑

⑤ 汇总最终结果
   → 调度校验脑审核
   → 输出给用户

⑥ 空闲时
   → 触发记忆巩固
   → 触发评估脑（创建实例 → 评估 → 自毁）

⑦ 权重进化
   → 记录每次任务的副脑表现
   → 强化/弱化权重
```

### 5.6 权重进化机制

```
初始状态: 所有副脑对所有类型任务权重 = 0.5

每次任务完成:
  1. 主脑记录: {task_type, agent, relevance, quality}
  2. 调整权重:
     - 相关且质量高 → 权重 += 0.1 (强化)
     - 相关但质量低 → 权重不变
     - 不相关 → 权重 -= 0.05 (弱化)
  3. 权重范围: [0.1, 1.0]
  4. 主脑下次调度时优先咨询高权重副脑

类比: 赫布定律 — "一起激发的神经元连接更强"
```

## 六、技术分层

### Rust 层 (核心运行时)

```
Rust 层职责:
├── 三通道消息总线 (tokio broadcast + mpsc)
│   ├── 通道1: broadcast channel (广播)
│   ├── 通道2: mpsc channel (协作，带路由)
│   └── 通道3: mpsc channel (结果汇总)
├── Agent 生命周期管理 (spawn/schedule/shutdown)
├── 权重引擎 (实时计算和存储)
├── 快思考引擎 (关键词匹配 + 经验检索)
├── 会话管理 (持久化、恢复)
├── CLI 入口 + HTTP API 服务 (axum/actix)
├── 配置系统
└── MCP 协议实现 (参考 claw-code-parity)
```

### Python 层 (AI 能力)

```
Python 层职责:
├── LLM 调用层 (多 Provider: Anthropic/OpenAI/本地模型)
├── 慢思考引擎 (推理/总结/审查)
├── 感知脑 LLM 解析 (haiku 级模型)
└── 通过 MCP 协议与 Rust 通信

注意: 初期不使用向量数据库
├── 记忆检索基于纯文件 + 关键词索引
├── 向量数据库在记忆 > 10000 条且召回率 < 70% 时再引入
└── 届时作为可选 Python MCP Server 插件
```

### 通信方式

```
Rust ←→ Python 通信:
├── MCP 协议 (推荐) — Rust 作为 MCP Client, Python 作为 MCP Server
├── FFI (备选) — PyO3 直接调用
└── HTTP (备选) — 本地 REST API
```

## 七、自然进化机制

### 7.1 新副脑的诞生

```
触发条件:
  1. 某类任务反复出现，现有副脑处理效率低
  2. 主脑检测到某类任务的处理质量持续低于阈值
  3. 用户手动创建新副脑

创建流程:
  1. 定义副脑的基础 prompt（核心规则）
  2. 注册到广播通道(通道1)和结果通道(通道3)
  3. 初始权重 = 0.5
  4. 开始接收广播消息
  5. 通过经验积累逐步提高专项能力
```

### 7.2 副脑的退化

```
触发条件:
  1. 某个副脑的权重持续低于 0.2
  2. 连续 N 次任务都不相关

处理方式:
  - 不删除，而是进入"休眠"状态
  - 休眠副脑不订阅广播通道，减少资源消耗
  - 当相关任务出现时可以"唤醒"
```
