# AI Brain 架构重构 — 设计讨论记录

## 背景

用户测试 AI Brain CLI 后发现核心问题：
1. 多轮对话没有上下文（问完天气说"宁波"，系统只记录位置不查宁波天气）
2. 工具调用只显示名称，不显示参数和结果
3. 记忆注入对用户不可见
4. 缺少详细的运行时日志
5. 整体响应慢（70+ 秒）、准确率差（答非所问）

## 核心目标

**打造一个能够日夜不停持续运转的 AI 大脑。**
踩过的坑不重复踩，用户纠正过的不重复犯。

---

## 架构决策：一主二从

```
         用户
          │
          ▼
    主脑（主力 LLM）────────────────── 全权负责所有任务处理
     │         │
     │         │ 所有交互实时落盘存储
     │         ▼
     │    记忆脑（监听者）─── 被动监听，不打断主脑
     │         │
     │         ├─ 每 N 轮用户输入做一次四层分析
     │         ├─ 上下文满时 → 清空 → 注入总结继续
     │         └─ 维护踩坑库、用户画像、自进化规则
     │
     └────────→ 评估脑 ─── 基于记忆脑的分析结果做质量审核
                    │
                    ├─ 检查是否重复踩坑
                    ├─ 检查是否违反用户偏好
                    ├─ 检查是否重复已知失败模式
                    └─ 反馈插入主脑对话历史
```

### 删除的组件
- 感知脑 (brain-sensory) — 主脑直接处理用户输入
- 执行脑 (brain-motor) — 主脑自带 tool_loop
- 校验脑 (brain-validation) — 评估脑承担
- 评估脑 (brain-evaluation) — 合并到新评估脑
- 进化脑 (brain-evolution) — 记忆脑的自进化机制替代
- 广播总线 (brain-bus) — 不再需要

---

## 主脑（主力 LLM）

等同 Claude Code 的主模型，唯一的 LLM 循环。

### 职责
- 直接接收用户原始输入
- 带完整对话历史 + 工具定义，跑 tool_loop
- 是唯一跟用户交互的
- 对标 Claude Code 的 messages 构造：全量历史，不每次重建

### Messages 构造
```
[system_prompt]                          ← 固定，缓存友好
[tools]                                  ← 固定，缓存友好
[user: "今天天气怎么样"]                   ← 历史
[assistant: text + tool_use(WebSearch)]  ← 历史
[tool_result: "北京19°C多云..."]          ← 历史
[assistant: "北京今天19°C..."]            ← 历史
[user: "我是宁波的"]                      ← 当前输入
```

### 内置工具
- 文件操作: read_file, write_file, edit_file
- Shell: bash
- 搜索: web_search, grep, glob
- MCP 扩展工具

## 记忆脑（常驻后台 — 静默触发）

**跟主脑一起启动，常驻运行，大部分时间静默。条件满足时触发执行。**

### 触发时机
- **每 N 轮用户输入**（如 10 轮）→ 触发四步分析
- **上下文 > 80%** → 强制触发，用已有总结重建上下文

### 工作方式
记忆脑持续监听主脑的所有交互（落盘存储）。
条件满足时，取出最近 N 轮对话 + 已有记忆数据，
用独立 LLM 调用 + 专用 system prompt 执行四步分析。

### 四步分析（顺序执行，每步依赖前步输出）

#### 第一步：事实总结（做了什么）
"用户问了天气，调了 WebSearch，查到北京 19°C，用户纠正说是宁波"

#### 第二步：在总结基础上 → 分析用户画像
- **显性信号**: "用 Rust"、"不用 TODO"、"回答要简洁"
- **隐性信号**: 用户在宁波、偏好中文、不耐烦长篇解释、工作时段活跃
- 持续累积，跨会话保留

#### 第三步：在总结基础上 → 分析踩坑点
- **工具调用失败**: WebFetch 超时 → 下次用 WebSearch 更稳
- **答案错误**: 回答了北京天气 → 用户纠正为宁波
- **格式问题**: 输出了英文 → 用户要求中文
- **偷懒行为**: 写了 TODO → 用户要求实际实现

#### 第四步：在前三步基础上 → 总结自进化规则
- "天气查询需要先确认用户位置"
- "read_file 结果太大时要截断"
- "用户说'不用 TODO'就是真的不能用 TODO"
- "调用 XXX 工具时参数必须是 YYY 格式，否则会报错"

### 存储方式
参考现有记忆脑设计（L1 全量 → L2 索引 → L3 经验包的分层存储）。

### 上下文管理策略

```
主脑每次调 LLM 前:
  │
  ├─ 估算当前 messages token 数
  │   ├─ < 60% → 正常发送（不压缩，最大化 KV Cache 命中）
  │   ├─ 60%-80% → 标记"下次需要压缩"
  │   └─ > 80% → 触发上下文重建
  │
  └─ 上下文重建流程:
      ├─ 清空主脑当前上下文
      ├─ 取记忆脑最近 N 轮的四层分析总结
      ├─ 注入为"上一轮会话内容"：
      │   [system_prompt]
      │   [tools]
      │   [user: "以下是之前的会话总结：{总结内容}。请基于这个上下文继续工作。"]
      │   [current_input]
      └─ 主脑从总结继续工作
```

### 总结内容的映射索引

总结中包含位置映射，方便找回原始内容：
```
"分析了 main.rs 行 50-100，发现 run() 函数缺少错误处理"
 → 索引: {file: "main.rs", lines: "50-100", storage_id: "raw_20260417_001"}

"调用 WebSearch('宁波天气') 成功，获取到宁波 22°C 晴"
 → 索引: {tool: "WebSearch", query: "宁波天气", storage_id: "raw_20260417_002"}
```

### 总结触发时机
- **按用户输入轮次**: 每 10 轮用户输入做一次总结
- **上下文阈值**: token > 80% 时强制触发

## 评估脑（常驻后台 — 静默触发）

**跟主脑一起启动，常驻运行，大部分时间静默。条件满足时触发执行。**
独立 LLM 调用。

### 触发时机
- 主脑每次产生最终输出后 → 自动触发评估

### 工作方式
评估脑持续等待主脑的输出。
触发时，取出主脑输出 + 记忆脑的踩坑库 + 用户画像，
用独立 LLM 调用 + 专用 system prompt 执行评估。

### 评估依据（来自记忆脑）

1. **踩坑库** — 已知的错误模式和解决方案
2. **用户画像** — 用户的偏好、禁忌、习惯
3. **自进化规则** — 总结出的避坑指南
4. **用户纠正记录** — 用户明确纠正过的事情

### 已删脑代码处理
- **代码删除**，不保留 crate
- **计划文档保留**，记录历史设计决策

```
主脑每次输出后，评估脑逐项检查：

  ├─ 是否重复踩坑？
  │   → "又回答北京天气？用户纠正过是宁波" ← 拦截
  │
  ├─ 是否违反用户偏好？
  │   → "用户说过要中文，你输出英文了" ← 拦截
  │
  ├─ 是否重复已知失败模式？
  │   → "这个工具调用上次超时了，你还用同样的方式" ← 拦截
  │
  ├─ 是否偷懒？
  │   → "写了 TODO 没写实现" ← 拦截
  │
  └─ 通过 → 输出给用户
```

### 反馈机制

发现问题时，反馈作为新消息插入主脑对话历史：
```
[assistant: "fn is_prime(n: u64) -> bool {\n    // TODO\n}"]
[evaluator: "⚠️ 你偷懒了 — TODO 不等于实现（用户纠正过多次）。
             请完成素数判断的实际逻辑。参考踩坑记录 #12"]
[assistant: "抱歉，补完：\nfn is_prime(n: u64) -> bool {\n    if n <= 1..."]
```

## LLM 底层机制参考

### KV Cache（模型层，服务端）
- 缓存 Transformer 注意力层的 Key/Value 矩阵
- 自回归生成时避免重复计算已生成 token 的 K/V
- O(n²) → O(n)，服务端自动做

### Prompt Caching（API 层）
- 跨请求复用前缀的 KV Cache
- Anthropic: 显式前缀缓存，TTL ~5 分钟，成本降 90%，延迟降 85%
- OpenAI: 自动缓存，最低 1024 token 触发，TTL 5-60 分钟
- Claude Code 前缀复用率 92%

### 对我们设计的影响
- **前缀不能频繁修改** — 否则缓存失效
- **上下文重建只断一次缓存** — 重建后的新前缀会被缓存
- **system_prompt + tools 永远不改** — 最大化缓存命中率
