# Phase 11 架构设计方案与对比

> 日期: 2026-04-09

## 一、需求总结

将 AI Brain Agent 从"单次查询→单次响应"的 demo 玩具，升级为**像人脑一样不间断执行任务的连续循环系统**。

### 核心需求

1. 持续循环执行：不是一次 query() 结束，而是持续到任务完成
2. 感知脑拆解任务：LLM 自主拆解 + 查询资源池推荐工具
3. 推理脑主导执行：LLM ↔ 工具调用循环，直接调工具
4. 步骤间智能压缩：记忆脑管理上下文，高价值保留、低价值压缩、原文可召回
5. 通用任务支持：编码、写作、信息收集、图片处理、视频剪辑等

### 确认的设计约束

| 约束项 | 决策 |
|--------|------|
| 执行模式 | 阶段式串行 |
| 任务拆解 | 感知脑 LLM 自主拆解（技能只是可选参考） |
| 工具推荐 | 感知脑查资源池后推荐 top 5 |
| 相关性判断 | step 级别（非 task 级别） |
| 工具调用 | 推理脑直接调（合并执行脑） |
| 人工介入 | 关键节点确认 |
| 完成标准 | 混合：量化指标 + LLM 评分 |
| 任务范围 | 通用 AI Agent |
| 持久化 | 记忆脑负责一切 |
| 技能来源 | 内置核心 + 用户自定义 SKILL.md |
| 上下文压缩 | 记忆脑负责（步骤间，非步骤内） |

## 二、架构方案对比

### 方案 A：技能驱动状态机

```
感知脑匹配技能 → 技能定义 N 个阶段(状态)
→ 主脑作为状态机引擎，逐阶段推进
→ 每个阶段：广播 → 副脑消费 → 收集结果 → 评估判定
→ 通过 → 下一阶段；未通过 → 重试当前阶段
```

| 优点 | 缺点 |
|------|------|
| 清晰可预测 | 技能必须预定义所有阶段 |
| 每阶段有明确进入/退出条件 | 灵活性受限 |
| | 新任务类型需要新技能 |
| | 任务拆解依赖技能而非 LLM |

### 方案 B：规划器-执行器循环（已选择）

```
感知脑 LLM 拆解 → 生成 TaskPlan（动态步骤）
→ 主脑循环执行：
    for step in plan.steps:
      分发 step 给推理脑（含推荐工具）
      推理脑 LLM ↔ 工具循环执行
      主脑 evaluate_step() 判定
      记忆脑持久化 + 压缩
→ 全部完成 → 交付
```

| 优点 | 缺点 |
|------|------|
| LLM 动态拆解，不依赖预定义技能 | 比方案 A 稍复杂 |
| 计划可持久化（中断恢复） | 需设计 Plan/Step 数据结构 |
| 评估脑发现方向不对可动态调整 | |
| 自然匹配 Superpowers 工作流 | |
| 通用性强（编码/写作/图片等） | |

### 方案 C：事件驱动 Actor 模型

```
取消"阶段"概念，纯事件驱动
每个副脑独立 Actor
技能定义事件响应模式
循环通过"任务未完成"事件自动触发
```

| 优点 | 缺点 |
|------|------|
| 最灵活 | 难以预测和调试 |
| 完全解耦 | 副脑间交互复杂 |
| | 对用户不够透明 |
| | 和人脑认知模型差距大 |

## 三、副脑精简决策

### 精简过程

| 副脑 | 最终决定 | 理由 |
|------|---------|------|
| 感知脑 | ✅ 保留 | 核心：理解、拆解、推荐 |
| 主脑 | ✅ 保留 | 核心：编排、评估 |
| 推理脑 | ✅ 保留（职责扩大） | 合并执行脑，直接调工具 |
| 记忆脑 | ✅ 保留（职责扩大） | 新增上下文压缩 + Plan 持久化 |
| 执行脑 | ❌ 合并到推理脑 | 推理脑直接调工具更高效 |
| 校验脑 | ❌ 降级为 guard_check() | 简单的前置检查，不需要独立副脑 |
| 评估脑 | ❌ 职责分散 | 评估归主脑，压缩归记忆脑 |
| 进化脑 | ❌ 暂时移除 | 新架构下权重进化意义不大 |

### 评估脑压缩功能归入记忆脑的理由

用户要求的压缩效果（智能判断价值、原文保存、可召回）远超 runtime::compact 的能力。
记忆脑是管理"记忆"的自然归属——工作记忆（上下文窗口）也是记忆的一部分。
类比人脑：海马体管理工作记忆→长期记忆的巩固过程。

## 四、新架构完整数据流

```
Phase 1: 感知 (Perceive)
─────────────────────────
用户输入 → 感知脑:
  ① LLM 理解任务意图
  ② LLM 自主拆解为步骤列表
  ③ 查询资源池（技能库 + MCP + 插件）
  ④ 根据任务 + 拆解内容 → 推荐 top 5 工具
  输出: TaskPlan { steps[], recommended_tools[] }
  → 用户确认计划 ✓

Phase 2: 执行循环 (Execute Loop)
─────────────────────────────────
主脑 for step in plan.steps:
  ① 记忆脑注入上下文（召回相关记忆、上一轮摘要）
  ② 记忆脑检查上下文使用率，> 阈值 → 压缩瘦身
  ③ 分发当前 step 给推理脑（含推荐工具列表）
  ④ 推理脑执行 LLM ↔ 工具调用循环
     - LLM 思考 → 调工具 → 观察结果 → 继续思考
     - guard_check() 拦截高危操作 → 弹给用户确认
     - 按需查询记忆脑（召回经验）
  ⑤ 推理脑输出 step_result
  ⑥ 主脑 evaluate_step() 评估完成度
     - 量化指标 + LLM 质量评分
     - PASS → 下一步 / FAIL → 重试或调整
  ⑦ 记忆脑持久化（step_result + 工具调用记录）
  ⑧ 如上下文膨胀 → 记忆脑触发压缩（步骤间，非步骤内）
  ⑨ 下一个 step...（循环）

Phase 3: 交付 (Deliver)
────────────────────────
所有 steps 完成 → 主脑最终评估 → 输出结果给用户
```

## 五、组件复用审计结论

### 可直接复用

| 组件 | 来源 | 复用方式 |
|------|------|---------|
| file_ops.rs (Read/Write/Edit/Glob/Grep) | runtime | 推理脑的工具执行底座 |
| bash.rs | runtime | 推理脑的 Bash 执行底座 |
| mvp_tool_specs() | tools | 生成 ToolDefinition 传给推理脑 LLM |
| MCP McpServerManager | runtime/mcp_stdio | MCP 工具发现和调用 |
| Plugin PluginTool::execute | plugins | 插件工具执行 |
| Skill 发现 + frontmatter 解析 | commands | 感知脑查询技能库 |
| 指令文件发现 discover_instruction_files() | runtime/prompt | 部分复用 |
| Prompt Cache (本地) | api/prompt_cache | 可复用缓存机制 |

### 需要改造

| 组件 | 来源 | 改造内容 |
|------|------|---------|
| brain-llm ChatRequest | brain-llm | 增加 tools/tool_choice 字段，content 升级为 Vec<ContentBlock> |
| brain-llm LlmProvider trait | brain-llm | 增加 stream_complete() 方法 |
| 感知脑 LlmProvider trait | brain-sensory | 统一到 brain-llm 的 trait |
| ToolExecutor trait | runtime | 支持异步 + Value 输入输出 |
| 消息总线 | brain-bus | 核心调用从通道改为直接方法调用 |
| System Prompt 构建 | runtime/prompt | 支持多副脑差异化 prompt |

### 全新实现

| 组件 | 原因 |
|------|------|
| 推理脑 tool_use 循环 | 当前完全没有，参考 conversation.rs 的 run_turn |
| 记忆脑上下文压缩 | runtime::compact 不满足需求（需智能判断+原文保存+召回） |
| TaskPlan 数据结构 | 新概念，包含 steps、推荐工具、执行状态 |
| 主脑 Plan 执行循环 | 当前只有单次 run_once |
| 感知脑任务拆解 + 工具推荐 | 当前只做输入解析 |
| guard_check() 函数 | 统一的前置安全检查 |
| evaluate_step() 方法 | 混合评估（量化+LLM评分） |
